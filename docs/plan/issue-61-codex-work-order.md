- Codex 조정·제작·검수 모델: `gpt-5.6-sol`, reasoning effort: `high`를 권장한다. 실행 환경의 모델 선택기에서 실제 사용 가능 여부를 확인한다. 모델이 없으면 사용 가능한 대체 모델을 명시하고, 조용히 바꾸지 않는다.
- 단순 파일 정리·내보내기는 `medium`으로 충분하다. `xhigh`는 승인 기록의 충돌이나 반복되는 복합 시각 결함을 분석할 때만 사용한다. 추론 강도를 이미지 생성 품질 설정과 혼동하지 않는다.
- 이미지 제작: 실행 환경이 제공하는 ImageGen을 우선 사용한다. 직접 Image API를 쓰는 승인된 환경에서는 `gpt-image-2`도 사용할 수 있으나, 실행 시점의 지원 모델·스키마를 확인한다. 실제 사용 모델을 기록하고, 도구가 공개하지 않는 모델 ID는 추정하지 않는다.
- 실제 이미지 생성, GitHub/로컬 파일 읽기, 이미지 열람, 브라우저 렌더링이 가능한 세션에서 실행한다. 프롬프트만 작성하는 세션을 제작 완료로 취급하지 않는다.
- CLI에서 해당 모델을 사용할 수 있을 때의 세션 실행 예:


### 3. 스킬과 도구 사용

시작 시 `/skills` 또는 환경의 스킬 목록에서 실제 설치된 이름과 기능을 확인하고, 사용할 스킬의 `SKILL.md`를 읽어라. 다음 이름이 모든 Codex 환경에 기본 설치되어 있다고 가정하지 마라.

- `playwright` 또는 동등한 브라우저 스킬/도구: 검토 HTML을 실제로 열고 이미지 로딩, 오버레이, 마스크, 중국어 줄바꿈, 캡처를 확인한다. 브라우저 검증 기능은 필수지만 특정 스킬 이름은 강제하지 않는다.

- `skill-installer`: 필요한 스킬이 없을 때만 사용한다. 출처를 검증하고 환경의 설치 승인 절차를 따른다. 비밀키를 출력하거나 저장소에 기록하지 마라.
- Creative Production의 `produce`: 설치되어 있고 보드 기반 검토가 가능한 경우에만 선택적으로 사용한다. 사용 시 해당 스킬의 보드·생성·검수 절차를 따른다. 이 작업에는 정확히 3개의 styleframe 방향만 필요하며, 기본 탐색 수량을 이유로 늘리지 마라. 이 플러그인이 없어도 실제 이미지 생성·검수 경로가 있으면 작업할 수 있다.

앱·클라우드·CLI 간 도구 접근성을 동일하게 가정하지 마라. 네이티브 이미지 생성이 없다는 이유로 임의 유료 서비스나 외부 API로 전환하지 마라. 승인된 실행 경로가 없다면 가능한 출처 조사·프롬프트·검토 틀을 남기되, styleframe 제작은 미완료로 보고하라. 스킬 설치나 프롬프트 작성만으로 생성 권한을 확보했다고 주장하지 마라.

사용한 스킬/도구, 사용 단계, 대체 수단, 사용 불가 기능을 최종 보고에 기록하라.

### 4. 이미 승인된 방향을 재선정하지 말 것

선택된 방향은 `daylight logistics`다. 3안은 다음과 같이 고정한다.

| 안 | 목적 | 통제할 차이 | 상태 |
| --- | --- | --- | --- |
| A — daylight logistics | 승인 방향의 실제 키 비주얼 검증 | 밝고 흐린 낮, 중광각의 전진 시점 | 선택된 방향 / 새 이미지 검토 대기 |
| B — dusk cinematic | 조명에 따른 분위기·가독성 비교 | A의 공간·카메라·재질을 최대한 유지하고 해질녘 조명으로 변경 | 비교 전용 / 비선택 |
| C — top-down technical | 위에서 보는 구도의 운영 가독성 비교 | 동일한 물류 세계를 높은 시점에서 재구성; 낮 조명 유지 | 비교 전용 / 비선택 |

B의 조명과 C의 시점은 비교 실험용 예외다. 이를 6개 장면의 공통 제작 상수에 섞지 마라. C도 사실적인 미니어처 디오라마여야 하며, 평면 청사진·인포그래픽·게임 맵으로 바꾸지 마라.

A의 방향이 승인되었다고 새로 생성한 A 이미지까지 승인된 것은 아니다. A가 검수에 실패하면 A를 수정하라. B/C가 일부 항목에서 더 좋아 보이면 그 사실과 A에 수용 가능한 교훈을 기록하되, 방향을 자율적으로 변경하지 마라.

### 5. 공통 시각 규칙

주인공은 중국 출발 컨테이너 야드다. 전경에는 컨테이너·출발 대기 팔레트·박스와 파란 경로 테이프를 두고, 중경에는 읽을 수 있는 이동 동선, 후경에는 다음 물류 단계를 예고하는 창고와 운송 경로를 둬라. 6단계를 한 장에 모두 집어넣지 마라.

약 1:87~1:100처럼 느껴지는 정밀 산업형 미니어처를 표현하라. 이 수치는 시각적 스케일 지침이며 생성 이미지에서 물리적으로 측정·보증한 축척이 아니다. 매크로/틸트시프트 느낌을 사용하되, 과도한 아웃포커스로 업무 흐름이 사라지지 않게 중간 심도를 유지하라.

무광 금속, 콘크리트, 골판지, 반투명 랩 필름, 도장 컨테이너, 고무 타이어와 철제 구조의 재질 차이가 보이게 하라. 콘크리트 회색·저채도 컨테이너 청색/적색·크라프트 갈색을 주조색으로 사용한다. A에는 밝고 흐린 낮의 확산광을 적용한다.

`#00ABE1`은 경로 테이프/선과 절제된 주의 유도에만 사용한다. 환경 전체를 청록색으로 물들이거나 경로를 네온·홀로그램처럼 만들지 마라. 재질과 조명에 의한 색 변화는 허용하되, 색상표와 UI 마스크 범례의 토큰값은 정확히 유지한다. UI의 주 CTA는 현재 토큰 `--action-primary`를 사용한다. 경로색과 버튼색을 무조건 동일시하지 마라.

인물은 스케일과 작업 맥락을 보조하는 소수의 작은 PPE 착용 작업자로 제한한다. 인물의 얼굴·개성·대형 로고가 주제가 되어서는 안 된다. 적재, 지게차 이동, 보행 동선과 물리적 접촉이 납득 가능해야 한다.

A에서는 앞으로 이동할 다음 공간과 컨테이너 모서리 같은 전경 가림 요소를 읽을 수 있게 구성한다. 정지 이미지로 실제 카메라 연속성까지 검증했다고 주장하지 마라.

금지 요소: 장난감 플라스틱, 수공예 모형 질감, 과대 브랜딩, 식별 가능한 실제 브랜드·항만·시설·주소, 가짜 중국어, 실제 운영 수치·자격·SLA, SF 홀로그램, 네온 과다, 군중, 위험 작업, 더러운 창고, 파손되거나 성립하지 않는 물류 과정, 공중에 뜬 화물, 객체 관통, 심한 반복 패턴과 녹아내린 바퀴/랙.

### 6. 무드보드 제작과 출처 추적

검토 가능한 무드보드 1세트를 만든다. 권장 분량은 출처가 분명한 시각 참조 8~12개다. 개수를 채우기 위해 관련 없는 이미지를 넣지 마라.

참조 축은 산업형 미니어처의 스케일, 흐린 낮 조명, 재질, 중성색 팔레트, 중국 출발 야드의 공간 구성, 파란 경로와 텍스트 여백이다. A의 승인 방향을 중심에 놓고 B/C는 작은 비교 영역으로 분리한다. 전체 이미지를 그대로 복제할 대상이 아니라 특정 속성의 참고로 사용하라.

각 참조에 `reference_id`, 원문 URL, 저작자/제공처, 접근일, 사용 조건을 확인한 URL, 확인된 사용 범위, 보드 포함 방식, 참고할 속성, 복제하지 않을 요소를 기록한다. 기존 레포 이미지도 출처와 사용 범위를 확인한다.

검색 결과 노출, 출처 표기, 워터마크 부재를 사용 허가로 간주하지 마라. 권리·재배포 조건이 불명확한 원본은 다운로드해 보드나 레포에 포함하지 말고 링크·메모만 기록한다. 공개 가능한 보드에는 허용 범위가 확인된 자산만 포함한다. 워터마크를 제거하지 마라. 링크만 있는 참조를 실제 이미지가 포함된 보드 타일로 계산하지 마라.

생성 참조를 쓰면 생성물임을 표시하고 모델·프롬프트·제공자 조건의 확인 위치를 기록한다. 실제 현장 사진인 것처럼 표시하지 마라. 최소 제작에 필요한 이미지 생성 예산이 없으면 무드보드용 추가 생성을 늘리지 마라.

### 7. styleframe 제작과 생성 기록

3안 모두 같은 종횡비·출력 크기·검토 품질을 사용한다. 목표는 16:9, 2048×1152 PNG다. 이는 이번 비교를 위한 작업 규격이지 최종 웹 미디어 전달 명세가 아니다.

실제 생성 도구가 해당 규격을 지원하지 않으면 지원하는 원본을 보존하고, 늘이기 없이 검토용 16:9 버전을 별도로 만든다. 크롭/확장/리사이즈 방법과 원본·출력 크기를 기록하고 핵심 객체와 안전영역을 재검수한다. 업스케일된 이미지를 네이티브 해상도로 보고하지 마라.

먼저 공통 공간·객체·재질·인물 밀도와 A의 카메라·조명을 문서로 고정한 뒤 A를 생성하라. 유효한 A가 있으면 이를 B의 재조명 기준으로 활용할 수 있다. C는 같은 물류 세계의 객체 구성과 동선 관계를 유지하며 높은 시점으로 재구성한다. 이미지 편집에 사용할 실제 파일과 해시를 기록하라. 단순 색 필터만 적용한 결과를 별도의 제작안으로 포장하지 마라.

각 안은 원칙적으로 최초 생성 1회와 결함 수정 1회 이내로 제한한다. 이번 styleframe 생성·편집 요청은 합계 6회 이내를 기본 상한으로 한다. 지원되지 않는 요청의 반복 호출과 취향만을 위한 무한 재생성을 하지 마라. 상한 내에서 실패한 항목은 숨기지 말고 미완료 사유를 제출하라. 무드보드용 추가 이미지 생성도 실행 환경의 승인된 예산에 포함해 관리한다.

다음 프롬프트 패키지를 작성하고 실제 호출과 연결하라.

- 공통 `master` 프롬프트.
- `scene-01`의 객체·공간·전진 방향 delta.
- A/B/C별 변경점과 변경하지 않을 점.
- 공통 negative prompt와 금지 요소.
- 이미지 입력 ID/파일, 생성·편집 모드, 실제 적용 인수.

도구가 negative prompt를 별도 인수로 받지 않으면 실제 지원되는 입력 방식에 금지 조건을 통합한다. 지원하지 않는 seed, 고정 카메라 인수, 품질 인수를 만들어 호출하지 마라. seed가 제공되지 않으면 `null` 또는 `not_exposed`로 기록한다. 기록이 같은 프롬프트의 픽셀 단위 재현을 보장한다고 주장하지 마라.

### 8. 안전영역과 중국어 UI 오버레이

원본 3장에는 핵심 중국어 카피, 단계 라벨, CTA를 구워 넣지 마라. 단계가 중국 출발임은 검토용 UI 라벨과 함께 확인한다. 실제 항만 표지·국기·가짜 한자로 중국 출발을 억지로 표현하지 마라.

각 안마다 다음을 분리한다.

- 텍스트 없는 clean 이미지.
- 동일 viewBox를 사용하는 SVG 안전영역 마스크.
- 이미지 기준 정규화 좌표의 `safe-areas.json`.
- 실제 HTML 텍스트/버튼을 겹쳐 렌더한 검토본.

안전영역에는 헤더, 히어로 제목·설명·CTA, 단계 안내 영역을 포함한다. 최초 구도는 좌측 약 35~40%를 낮은 시각 밀도의 텍스트 영역으로 검토하되, 실제 IA와 중국어 줄바꿈에 맞춰 조정하고 최종 좌표를 기록하라. 영역 안의 박스, 경로선, 고대비 모서리와 텍스트가 경쟁하지 않게 하라.

카피는 승인된 레포 콘텐츠를 사용한다. 미확정 카피밖에 없으면 검토용 임시 문구임을 캡션과 메타데이터에 표시하고, 이미지 안에 넣지 마라. 가독성 비교에는 3안에 동일한 카피·폰트 크기·줄바꿈 기준·UI 배치 규칙을 사용하고 변경이 필요한 부분은 기록한다.

폰트와 UI 색상은 현재 디자인 시스템/토큰을 재사용하고 원본 토큰을 변경하지 마라. 임시 검토본 때문에 전역 스타일을 수정하지 마라. 중국어 폰트 누락, 글자 깨짐, 잘림과 버튼 충돌을 확인한다. 반투명 패널·그라데이션을 추가하면 그 사용을 기록하고 clean 이미지 자체의 여백 문제를 숨기지 마라.

모든 생성물의 검토 캡션에 `概念示意`를 표시한다. 라벨은 이미지 바깥의 HTML/캡션 레이어에 둔다. 실제 PNPLINE 시설·항만·운영 사진으로 제시하지 마라.

### 9. 산출물 구조

기존 산출물 규칙이 없으면 다음 새 경로를 사용한다. 다른 규칙이 있으면 동등한 구조로 맞추고 README에 위치를 기록한다.

```text
output/scroll-world/issue-61-scene-01/
  README.md
  moodboard.png
  moodboard-sources.json
  scene-01-a-daylight.png
  scene-01-b-dusk.png
  scene-01-c-topdown.png
  comparison.png
  safe-areas.json
  masks/                      # 각 안의 SVG 안전영역
  prompts/                    # master, scene-01, variants, negative
  preview/index.html          # clean / mask / UI 오버레이 검토
  screenshots/                # 실제 브라우저 검토 캡처
  manifest.json
  qa.md
```

원본과 파생본이 다르면 `originals/`를 추가한다. 무드보드 편집 원본, 합성/마스크/내보내기 스크립트는 재사용에 필요한 최소 범위로 보존한다. 새로운 프런트엔드 앱·패키지 체계를 만들지 마라. 레포에 앱이 없으면 간단한 정적 검토 HTML이면 충분하다. 공개 배포하거나 프로덕션 라우트에 연결하지 마라.

README에는 열람 방법, 산출물 경로, A=선택 방향/B·C=비교 전용, 각 이미지의 검토 상태, 출처와 제약, 다음 승인 항목을 적어라. 이미지 파일만 넣지 말고 문서 또는 검토 페이지에서 바로 볼 수 있게 연결하라.

manifest에는 각 파일의 안/용도, 원본 여부, 실제 픽셀 크기, 바이트 크기, SHA-256, 생성/가공 도구, 노출되는 모델 ID, 프롬프트 경로, 입력 이미지, 생성 횟수, 후처리, 확인 가능한 비용과 승인 상태를 기록한다. 비용을 확인할 수 없으면 `unknown`으로 기록하고 0원으로 추정하지 마라. 비밀키·인증 URL·토큰은 기록하지 마라.

### 10. 검수와 완료 조건

각 이미지를 실제로 열어 원본 크기와 축소 크기에서 확인하라. 코드가 실행되었다는 사실을 시각 품질 검수로 대신하지 마라.

검수 항목은 산업 물류 인지, 미니어처 스케일, 재질 분리, 물류 동선의 설득력, 경로의 주의 유도, UI 텍스트 가독성, 과장된 운영 사실·브랜드 노출, 생성 결함이다. A에는 승인된 낮 조명·중광각 전진 구도를 추가로 검수한다. B/C에는 사전에 선언한 비교 예외를 적용한다.

A/B/C 비교표에는 장점, 약점, 결함, 안전영역 적합성, A에 반영할 수 있는 교훈을 적는다. A를 선택 방향으로 유지하되 실제 이미지 검수 결과를 왜곡하지 마라. 정성적 내부 검토를 실제 사용자 테스트나 계량 성능 검증이라고 표시하지 마라.

검토 HTML을 실제 브라우저에서 열고 적어도 1440×900, 390×844 뷰포트에서 이미지·캡션·중국어·마스크·오버레이 컨트롤의 로딩과 잘림을 확인해 캡처를 남겨라. 작은 뷰포트 검토는 검토 페이지의 사용성을 확인하는 것이며 모바일 키프레임을 제작·검증했다는 뜻이 아니다. 같은 안의 이미지·마스크·텍스트에 동일한 좌표 변환을 적용하라.

파일 디코딩, 경로, 픽셀 크기, 마스크 viewBox, 정규화 좌표 범위, 이미지·manifest 매칭을 확인하라. 최소 정적 검토 페이지를 위해 불필요한 테스트 프레임워크를 새로 설치하지 마라. 기존 테스트가 적용되는 코드를 변경했다면 관련 검사만 실행하고 명령·결과를 기록한다.

A의 별도 모바일 구도 원칙을 기록하라. 세로 프레임에서 팔레트·경로·후경 창고·UI 안전영역을 어떻게 재배치할지 설명하되 데스크톱 중앙 크롭을 모바일 제작안으로 취급하지 마라.

카메라 연속성, 장면 전환, scroll seeking, 영상 성능, 모션 감소 전환은 이번에 검증하지 않았다고 표시하라. A가 정적 fallback 후보라는 설명과 fallback 구현 완료를 구분한다.

완료는 실제 무드보드와 styleframe 3장, 3안의 안전영역·오버레이, 출처 기록, 생성 기록, 비교 검수와 브라우저 캡처가 모두 존재할 때만 선언한다. 사용자의 이미지 승인 전 상태는 `review_pending`이다. 생성·브라우저 권한 문제나 품질 결함으로 미달하면 부분 완료와 미완료를 분리해 보고하라.

### 11. 최종 보고와 저장소 변경 제한

최종 응답은 무드보드와 3안의 실제 미리보기 또는 로컬 산출물 링크로 시작하고, 각 안의 차이·검수 결과·남은 결함을 보고하라. 사용한 모델/effort/스킬, 작업 SHA, 생성·수정 횟수, 파일 크기와 확인 가능한 비용, 실행한 검증을 함께 남겨라.

A는 승인된 방향이지만 새 이미지의 사용자 승인은 대기 중이라는 점을 명시한다. 후속 작업은 선택 이미지 검토 → 6개 데스크톱 및 별도 모바일 키프레임 확장 → 애니매틱 → #24 파일럿 순서로 기록한다.

#61 전체를 닫거나 전체 완료로 체크하지 마라. `Closes #61`/`Fixes #61`을 쓰지 마라. 필요하면 `Refs #61 — partial deliverable`로 표시한다. 별도 요청 없이 GitHub 이슈 댓글 작성, PR 게시, push, merge, 배포를 하지 마라. 이번 산출물 때문에 디자인 시스템·토큰·승인 기록을 임의로 바꾸지 마라.
