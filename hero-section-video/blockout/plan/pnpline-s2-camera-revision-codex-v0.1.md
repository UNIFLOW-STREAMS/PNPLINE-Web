# PNPLINE S2 카메라워크 수정 — Codex 지시서 v0.1

## 1. 목적과 작업 기준

기존 Blender Master에서 S2 「중국 항구와 출항」의 카메라워크를 첨부 러프 스토리보드 S2-01~S2-05의 화면 전개와 유사하게 수정하라.

목표 흐름:
주인공 컨테이너와 갑판 근경 → 후퇴·상승하며 주변 적재부 공개 → 선박과 중국 항구의 관계 공개 → 선미 쪽으로 돌아 출항에 합류 → 선미·선측·선수 방향의 깊이가 읽히는 후방 사선 추적.

다섯 그림은 연속 이동의 관찰 지점이지 다섯 컷, 다섯 대의 카메라, 다섯 번의 정지 지점이 아니다. 상세 모델링·재질·브랜딩을 복제하는 작업으로 확대하지 않는다.

레포: https://github.com/UNIFLOW-STREAMS/PNPLINE-Web
작성 시 조회 기준: main@6079b392d7de54509ed50454ddd2745273cc0078
관련 맥락: 기존 Master의 7구간 연출안 검증. 기존 #61 승인안의 변경이나 최종 영상·운영 공개 승인이 아니다.

실제 수정 기준은 실행 환경의 사용자 작업 브랜치·HEAD·현재 사용 중인 .blend 및 생성 스크립트다. 시작 시 버전·해시·미저장/미커밋 변경을 확인하고, 위 조회 기준과의 차이를 기록한다. 녹화 영상이 위 커밋의 결과와 동일하다고 가정하지 않는다. 강제 checkout/reset을 하지 않는다.

## 2. 필수 입력과 사전 조사

### 입력
- 현재 상태 녹화: `bandicam 2026-10-07 01-22-53-539.mp4`
- 목표 관찰 이미지: `s2-01.png`, `s2-02.png`, `s2-03.png`, `s2-04.png`, `s2-05.png`
- 기존 편집 가능한 Master .blend와 해당 버전의 생성/검증 스크립트.
- 기존 Master 지시서, S2 텍스트 원문 및 S1 종료·S3 시작 연결 조건.

인계 ZIP의 references/에는 녹화와 다섯 보드가 있다. ChatGPT 첨부가 Codex에 자동 공유된다고 가정하지 않는다. 편집 가능한 .blend는 이 ZIP에 포함하지 않았다. 현재 작업 파일 또는 레포에서 확인한다. 입력이 없으면 해당 자료를 요청하고 영상만 보고 새 세계를 다시 만들지 않는다.

### 먼저 확인할 사항
1. 적용되는 AGENTS.md, 현재 소스 .blend·생성기의 관계, 사용자의 수동 편집 여부.
2. 녹화가 본편 CAM_MASTER의 카메라 뷰인지 다른 사용자 뷰인지. 저장본에서 S2를 출력해 녹화와 먼저 대응시킨다.
3. 실제 S2 프레임 범위·FPS·B12/B23·카메라 이름·렌즈·시선 제어·보간 방식.
4. 실제 선박의 선수/선미/해측 방향과 항구 위치. 화면 좌우나 임의의 월드 X축으로 추측하지 않는다.
5. 원본 .blend 저장 및 새 버전 출력이 가능한 Blender 실행 환경. 모델 선택이 Blender 연결이나 실행 권한을 대신하지 않는다.

녹화 파일은 약 7.70초, 231프레임, 약 30fps, 1576×880이다. 이것은 녹화 특성이다. 아래 레포 타임라인과 같다고 간주하지 않는다.

## 3. 확인된 차이와 원인 조사 범위

### 녹화에서 관찰한 화면 차이
- 초반: 주인공 컨테이너 전면에 가까운 넓은 측면이 중심이고 주변 적재물과 크레인이 보인다. 보드의 큰 좌측 선교와 갑판 깊이의 구성이 충분히 읽히지 않는다.
- 녹화 약 2~4초: 선박 전체가 비교적 빨리 작은 크기로 들어오고, 항구를 내려다보는 화면으로 넓어진다. 보드 S2-02~03은 아직 선박이 전경을 크게 차지하며 부분적으로 잘려 있다.
- 녹화 약 4~6.5초: 측후방으로 시점은 변하지만, 작은 선박을 위에서 내려다보는 구도로 수렴한다. S2-05처럼 가까운 선미와 선수로 이어지는 긴 갑판의 깊이가 크게 읽히지 않는다.
- 녹화 끝의 정지 화면은 촬영·재생 정지일 수 있다. 이것만으로 원본 카메라의 ease-out 또는 실제 타임라인 정지로 진단하지 않는다.

이 시간은 녹화상의 위치 표시다. Blender 키프레임 번호로 자동 환산하지 않는다.

### 코드에서 확인한 구현 — 현재 파일과 재대조
`build_master.py` 기준:
- S2/B12는 f96, S3/B23는 f216이며 FPS=12다.
- 본편 카메라 `CAM_MASTER`, 시선용 `CAM_LOOK_TARGET`을 사용한다.
- 선박 로컬 선수는 +X, 선미는 -X다. 해측 카메라 방향은 기존 manifest상 로컬 -Y다.
- `camera_anchor()`, `camera_keys`, `target_keys`, `spline()`으로 전체 경로를 구성한다.
- S2 주변 앵커에는 f80·110·160·216·270이 있다. f110은 (5,-16,10), f160은 (-5,-25,17), f216은 (-17,-26,19)이며 이는 SHIP 공간 입력이다. 이 값은 기존 상태 설명이지 수정 목표값이 아니다.
- 앵커는 해당 시점의 선박 지역 변환으로 월드 좌표가 된 뒤 전체 spline에서 보간된다. 앵커의 로컬 오프셋만 보고 중간 경로까지 검증됐다고 하지 않는다.
- 경로를 프레임별 위치·Quaternion 회전 키로 베이크하고, 저장 키의 보간을 LINEAR로 설정한다.
- S2의 렌즈는 기준 40mm다. 기존 렌즈 애니메이션은 S4에 해당하는 f476~555에 별도로 있다.

따라서 이번 수정의 첫 대상은 단순한 “LINEAR → BEZIER 변경”이 아니다. 카메라와 시선의 경로·거리·높이·선박 상대 방위·진행 속도를 먼저 수정하고 실제 평가 결과를 검증한다. 모든 베이크 키에 ease in/out을 일괄 적용하지 않는다.

### 카메라만으로 해결되지 않는 부분
레포 프록시의 `SHIP_BRIDGE`는 상단 컨테이너보다 낮은 구조다. 보드의 선교는 적재물 위로 크게 솟아 있다. 긴 선체·적재열 비례도 보드와 다르다.

이 차이는 카메라 오류와 분리한다. 현재 형상을 유지하며 가능한 구도 유사성을 높이되, 선교를 키우거나 선박을 늘여서 카메라 수정으로 보고하지 않는다. 모델 보강이 꼭 필요한 목표는 “형상 제약으로 미충족”과 최소 보강 제안으로 남긴다.

## 4. 변경 범위와 보존 조건

허용:
- S2 카메라 위치 경로, 시선 목표 경로, 회전/롤 안정화, 속도 분배와 보간.
- 필요한 최소 카메라 제어점·가이드와 회귀 검사.
- 기존 프레임 범위 안에서 다섯 관찰 지점에 대응하는 프레임 선택·조정.
- 카메라 수정분을 재현하는 소스 변경, 새 버전 .blend와 증거 출력.

기본 보존:
- 지구 반지름, 양국 지형·부두·도시·창고 배치, 애셋 형상·재질·개수·컨테이너 적재 위치.
- 선박의 경로·자세·출항 시점, 크레인·스프레더·화물의 움직임.
- 전체 FPS·구간 경계 프레임·총길이.
- S2 바깥의 카메라와 모든 비카메라 평가 상태.
- B12/B23에서 이어지는 화면·속도·시선의 연속성.

렌즈는 먼저 기존 값을 유지하고 공간상 후퇴·상승과 시선 이동으로 해결한다. 렌즈를 바꿔야 한다면 이유와 경계/다른 구간 영향을 별도 제안한다. 줌만으로 화면을 줄이거나 극단적인 광각으로 선체를 길게 보이게 하지 않는다.

금지:
- 보드에 맞추기 위해 선박을 회전·확대하거나 항구를 반대편으로 이동.
- 서로 다른 카메라 컷, 거울 반전, 가림/안개를 이용한 숨긴 전환.
- 새 선박·도시·로고·물결 제작, 고급 재질·조명 작업.
- 보드의 대형 선체 PNPLINE 로고, 중국 항구 간판, 숫자·일련번호를 신규 제작 요구로 해석.
- Higgsfield 생성, 웹사이트/Three.js 작업, 운영 공개.

## 5. 다섯 관찰 지점의 목표 구도

각 이미지의 프레임 테두리·하단 메모를 제외한 장면 영역을 사용한다. 그림과 출력의 비율이 다르면 비율을 보존해 비교하고, 억지 늘이기나 중요한 선체를 자르는 후처리로 일치시키지 않는다.

### K1 — S2-01: 후퇴 지속 시작
- 주인공 컨테이너를 중심으로 긴 측면·끝면과 주변 적재부가 함께 읽힌다.
- 컨테이너만 꽉 채우기보다 앞쪽 적재물과 좌측 선교 방향의 깊이 관계를 확보한다.
- 선박 외곽 전체와 항구 전경을 처음부터 모두 보여 주지 않는다.
- S1에서 이미 진행 중인 후퇴를 이어받으며 S2 시작에서 다시 정지·출발하지 않는다.
- 현재 낮은 선교를 보드처럼 크게 보이게 만들기 위한 형상 변경은 하지 않는다.

### K2 — S2-02: 상승하며 선박 공개
- 같은 피사체·같은 관찰 측면을 유지하며 후퇴에 점진적 상승을 더한다.
- 주인공 컨테이너가 작아지는 동시에 주변 갑판·적재열·선교 방향이 더 많이 드러난다.
- 보드는 이 시점에도 선박 일부가 화면 밖이다. “선박 공개”라는 제목만 보고 여기서 선체 전체를 작은 크기로 넣지 않는다.
- 변화의 중심은 수직 상승 하나가 아니라 거리·높이·바라보는 중심의 점진적인 확장이다.

### K3 — S2-03: 중국 항구 드러남
- 선박의 가까운 선측과 갑판이 여전히 전경을 크게 차지하고, 뒤로 크레인·부두·야드·도시가 이어진다.
- 선박을 작은 중심 물체로 남긴 항구 탑뷰가 아니라 “이 선박이 이 항구에 있다”는 깊이 관계가 읽혀야 한다.
- 시선 중심은 주인공 컨테이너 한 점에서 적재부·선박 쪽으로 서서히 넓힌다. 선박 원점으로 순간 전환하지 않는다.
- 실제 형상과 배치가 허용하는 범위에서 수평선/원경을 남기고 과한 하향 구도를 줄인다. 수평선을 만들려고 세계·해안·배경을 새로 만들지 않는다.

### K4 — S2-04: 출항 전환
- 배경을 읽을 여유를 확보하되 카메라가 멈춰 있는 관광 전경으로 만들지 않는다.
- 해측의 안전한 바깥 경로에서 선미 쪽으로 이동하며 선박의 기존 출항 움직임에 합류한다.
- 선박이 부두에서 멀어지는 관계와 갑판·선측이 계속 읽혀야 한다.
- 뒤로 멀어지는 움직임만 계속하지 않는다. 이 지점부터 후방 추적을 위한 상대 방위를 만드는 데 비중을 둔다.

### K5 — S2-05: 후방 사선 추적
- 선미 면과 한쪽 선측, 선수 쪽으로 이어지는 갑판의 깊이를 함께 보여 준다.
- 선미가 전경, 선교·적재열이 중경, 선수 앞의 바다가 진행 방향으로 읽힌다.
- 보드처럼 선박을 주요 피사체로 크게 유지하되 선수·선미의 읽힘과 다음 이동 공간을 잃지 않는다.
- 기존보다 후방/측방 오프셋의 비율과 추적 거리를 조정해 “측면 와이드”가 아니라 “뒤에서 함께 따라간다”는 시점을 만든다. 구체적인 좌표는 실제 씬에서 결정한다.
- 카메라는 선박 진행에 합류한 상태로 S3에 이어진다. S2 종료를 이유로 완전히 감속·정지하지 않는다.

### 이미지 사이의 공간 불일치 처리
S2-03~04에서는 항구가 오른쪽 배경, S2-05에서는 왼쪽 배경에 보인다. 화면 좌우 변화 자체만으로 잘못이라고 단정하지 않는다. 같은 세계·같은 해측 경로에서 실제로 이렇게 보이는지 확인한다.

다섯 보드의 배경 배치가 하나의 연속 경로로 양립하지 않으면:
- 어떤 프레임의 어떤 관계가 충돌하는지 탑뷰와 비교 화면으로 설명한다.
- 같은 세계에서 가능한 가장 가까운 대안 구도를 별도 제시한다.
- 항구 이동·거울 반전·선박 반대편 순간 이동으로 몰래 맞추지 않는다.
- 필요한 원문/보드 변경을 사용자 결정으로 남긴다.

## 6. 경계와 보간의 핵심 제약

### B12/B23는 조사 전 무작정 잠그지도, 몰래 바꾸지도 않는다
기존 경계 화면이 이미 목표 첫/끝 구도와 다르면, 기존 경계 값을 완전히 고정하면서 보드와 같은 첫/끝 화면을 만드는 데 한계가 있다.

먼저 기존 B12/B23의 평가 위치·회전·시선·렌즈·직전/직후 속도를 기록한다. 이를 유지한 S2 내부 수정으로 목표가 가능한지 확인한다.

가능하면 S2 내부만 수정하고 S1/S3는 그대로 유지한다.
불가능하면 원본을 보존한 별도 S2 후보와 다음 정보를 제출한다.
- 변경이 필요한 경계와 기존/후보 상태 차이.
- S1 끝 또는 S3 시작에서 필요한 최소 카메라 접합 프레임 범위.
- 변경 없는 보존 구간과 다시 검증해야 할 항목.
- 경계를 보존하는 제한적 대안과 목표 구도를 우선하는 대안의 차이.

S1/S3 카메라 수정·경계 변경이 필요한 경우 승인 전에는 통합본을 완료 처리하지 않는다. S2 말미를 급히 원래 먼 구도로 복귀시키는 방식도 해결책으로 사용하지 않는다. 다른 구간의 의미 있는 연출 변경이나 전체 리타이밍은 이번 작업 범위가 아니다.

### 전역 spline의 주변 구간 영향
현재 `spline()`은 이웃 앵커로 접선을 계산한다. S2 앵커만 편집했다고 해서 S1/S3 평가값이 보존된다고 볼 수 없다.
- 수정 전후 전 구간의 실제 카메라·타깃·렌즈를 비교한다.
- 필요하면 범위 한정 보정 또는 경계 위치·접선을 보존하는 최소 구성으로 수정한다.
- 공용 spline 함수를 바꿔 선박/다른 장면까지 영향을 주는 리팩터링은 하지 않는다.
- GUI에서 베이크된 키만 수정하고 생성 소스는 그대로 남기는 불일치를 만들지 않는다.

### 속도·시선·기울기
- 다섯 보드마다 ease in/out을 적용해 멈칫거리는 다섯 동작을 만들지 않는다.
- 후퇴·상승·선미 방향 이동·추적은 겹쳐 이어지되 관객이 상태 변화를 읽을 시간을 둔다.
- 카메라 이동속도뿐 아니라 시선 목표의 이동과 각속도도 함께 확인한다.
- 위치가 부드러워도 타깃이 급변해 화면이 휘도는 경우는 실패다.
- 고정 월드 Z가 아닌 실제 지역/수면 방향과 카메라 up 처리도 확인한다. 축 선택 오류를 롤 보정으로 덮지 않는다.
- 상수 렌즈·안정적인 롤을 우선하고 필요 없는 틸트·급회전·바운스는 넣지 않는다.

## 7. 실행 순서

T1 — 기준 재현과 실패 기록
원본을 보존하고 실제 카메라 출력과 녹화를 대응시킨다. S2 전체, B12/B23, 카메라 상대 위치·점유율, 환경/선박 상태를 기록한다. 관련 기존 테스트를 먼저 실행해 기존 실패와 새 실패를 구분한다.

T2 — 다섯 목표 구도와 경계 가능성 확인
기존 단일 씬에서 K1~K5의 카메라 후보를 만들고 대응 프레임을 정한다. 다섯 이미지에 균등 시간을 강요하지 않는다. 모델 비례·부두 위치 때문에 불가능한 항목을 카메라 문제와 분리한다. 필요한 경계 변경은 6장의 절차대로 보고한다.

T3 — 최소 카메라 경로 수정
위치·타깃·방위·거리의 연속 경로를 구성하고 기존 구간 길이 안에서 속도를 분배한다. 키 수·내부 함수 구성은 구현자가 조정하되 변경 범위를 최소화한다. 스크립트 변경에는 실패를 먼저 재현하는 범위/경계 회귀 검사를 추가한다.

T4 — 렌더와 실제 동작 검토
동일한 출력 조건에서 수정 전후 S2를 정상 속도로 재생해 비교한다. K1~K5 스틸과 그 사이 움직임을 함께 검토한다. S1 말미→S2 전체→S3 초반도 연결 재생한다. 전역 경로 영향이 발생하면 전체 타임라인 검사와 필요한 추가 프리뷰를 수행한다.

T5 — 재개방·diff·증거 정리
저장본을 새 Blender 프로세스로 열어 수정 결과가 유지되는지 확인한다. 소스/씬/검증 데이터가 같은 버전인지 확인하고 결과를 보고한다. 과거 보고서의 성공을 현재 수정의 증거로 재사용하지 않는다.

## 8. 수용 기준

AC-1 — 기준과 입력
현재 .blend·소스·커밋·해시·S2 범위·FPS·보드 버전·녹화 대응을 기록한다. 화면 캡처를 Blender 시간축으로 추정한 값은 기준으로 사용하지 않는다.
검증: 원본 재현 화면과 입력/환경 기록.

AC-2 — 다섯 관찰 상태의 유사성
K1~K5가 순서대로 존재하고, 각 단계의 주요 대상·가시 면·깊이·배경 공개·크롭 관계가 5장의 목표 조건에 대응한다. K2에서 갑자기 작은 전체 선박으로 바뀌지 않고 K5는 큰 후방 사선 추적으로 읽힌다.
검증: 보드/수정 전/수정 후의 5행 비교표와 실제 대응 프레임. 형상 때문에 남는 차이와 카메라 미달을 분리한다. 픽셀 유사도 점수 하나로 통과시키지 않는다.

AC-3 — 연속성과 속도
컷·시점 재설정·반대편 순간 이동·관찰 지점마다 정지·급격한 롤/타깃 전환이 없다.
검증: S2 연속 재생, 위치·회전·타깃·렌즈의 전 프레임 값과 속도 변화. 근접/전환 지점은 서브프레임도 확인한다.

AC-4 — 선박·환경 보존
비카메라 오브젝트의 형상·재질·위치·애니메이션·컨테이너 적재 관계가 보존된다. 가이드 추가는 검토 전용으로 구분한다.
검증: 수정 전후 오브젝트/데이터 비교와 평가 변환 비교. 가독성을 위해 배나 항구를 움직였으면 실패다.

AC-5 — 관통·가림
카메라가 컨테이너·선교·선체·크레인·지형을 관통하지 않고 주요 피사체를 뜻하지 않게 잃지 않는다. near clip으로 물체 일부를 잘라 보이게 하는 편법도 없다.
검증: 실제 크기의 카메라 경로와 점유 공간 검토, 근접 구간 화면 및 필요한 충돌/가시성 샘플. 검사 해상도와 한계를 밝힌다.

AC-6 — S1/S3 및 나머지 구간 회귀
미승인 구간은 수정 전과 동일하며 B12/B23가 자연스럽게 연결된다. 필요한 경계 변경이 승인 대기이면 이 AC는 미충족/판정 보류다.
검증: S1 말미→S2→S3 초반 프리뷰, 전 구간 카메라/타깃/렌즈 비교, 승인된 변경 범위 밖 값의 보존 검사.

AC-7 — 재현과 전달
새 .blend를 재개방해 같은 구도·동작이 재현되고, 생성/수정 소스·경계 기록·출력·해시가 일치한다.
검증: 재개방, 대표 프레임 재출력, 소스 diff와 실제 검사 로그. 필수 AC가 미검증이면 완료라고 하지 않는다.

정량 보조 기록:
K1~K5에서 선박·주인공 컨테이너의 정규화 화면 위치/경계상자, 선미/선수 가시성, 카메라의 선박 상대 거리·방위·높이, 렌즈를 기록한다. 가려진 부분을 포함한 투영 경계상자는 실제 가시성 검증과 구분한다. 임의의 “95% 유사도”나 근거 없는 고정 mm/각도 목표를 만들지 않는다.

## 9. 검증 명령과 산출물

기존 README의 Blender 백그라운드 검사 및 렌더 절차를 참고하되 바이너리·Python·ffmpeg·경로를 실행 환경에서 재확인한다.
우선 조사/사용할 기존 도구:
- `scripts/test_scene.py`
- `scripts/export_validation.py`
- `scripts/render_review.py`
- `scripts/verify_reopen.py`

기존 `build_master.py`는 씬을 초기화하고 ROOT 하위 생성 산출물을 덮어쓰는 구조다. 미저장 GUI 작업·현재 원본에 바로 실행하지 않는다. 안전한 버전별 작업 복사본에서 실행하고 기존 결과를 보존한다.

새 출력 이름 예시 — 현재 존재 경로가 아닌 제안:
- `master-s2-camera-v001.blend`
- `preview/s2-before.mp4`, `preview/s2-after.mp4`
- `preview/s1-tail_s2_s3-head.mp4`
- `review/K1~K5` 비교 스틸과 카메라 경로 탑뷰/사선뷰
- `camera-before-after.json`: 범위·변환·타깃·렌즈·경계·속도 비교
- `report-s2-camera.md`: 변경·AC·미결·한계·명령·파일 해시
- 실제 변경 소스/patch 및 추가 회귀 검사

수정된 파일명과 scene metadata 버전은 구분한다. 기존 테스트의 `master_version == v001` 같은 버전 검사는 새 버전 정책에 맞춘 명시적 기대값 수정만 허용하며, 행동·연속성 기준을 느슨하게 바꾸지 않는다.

비교 영상은 같은 FPS·해상도·속도 기준으로 출력한다. 본편 렌더와 가이드가 있는 검토 화면을 구분한다. 보드의 선화·파도·선박 로고를 따라 그리지 않는다. 무관한 웹 빌드·SEO·배포 검증은 수행하지 않는다.

## 10. 중단 조건·보존·결과 보고

중단 또는 해당 변경 승인 대기:
- 현재 .blend와 생성 소스의 정체·버전이 불명확하거나 필수 입력이 없다.
- 요구된 구도를 위해 선교/선체 형상, 항구 배치, 선박 동작 또는 S1/S3 연출 변경이 필요하다.
- 현재 구간 길이 안에서 관통·급회전 없이 경로를 연결할 수 없어 시간 변경이 필요하다.
- 새로운 유료 서비스·설치·권한 확대·보안 위험·파괴적 변경이 필요하다.

표현 가능한 카메라 내부 조정은 이유를 기록하고 진행하되 위 조건을 몰래 우회하지 않는다.
테스트 삭제·비활성화·규칙 완화로 통과를 꾸미지 않는다.
비밀키·실제 개인정보를 코드·로그·샘플에 넣지 않는다.
기존 무관한 변경을 보존한다.
승인 없는 운영 데이터 변경·운영 배포·유료 호출·강제 푸시·무관한 변경 덮어쓰기를 금지한다.
라이브러리 추가는 이유·영향을 보고한다. 별도 요청 없는 커밋·push·PR·이슈/노션 수정은 하지 않는다.

보고에는 다음을 포함한다.
- 판정: 수용 가능 / 재작업 필요 / 증거 부족으로 판정 보류.
- 기준/결과 버전, 파일 목록·diff·.blend 해시.
- K1~K5별 개선과 남는 차이, 카메라/형상 제약 구분.
- AC별 상태·프레임·영상·검사 증거.
- 명령·환경·성공/실패, 기존/신규 실패, 미실행 검증과 이유.
- B12/B23 변경 필요 여부와 S1/S3 접합의 승인 상태.

## 11. 모델·추론 노력·스킬

권장 실행: 단일 작성 에이전트, GPT-6 Astra, High.
처음에 전역 spline의 영향 범위와 B12/B23의 공간적 충돌을 해결해야 하면 해당 조사/경로 설계 단계에 Extra High(xhigh)를 사용하고, 결정된 경로의 반복 수정·렌더 확인은 High로 진행하는 구성을 권한다. 이 설정은 작업 난도에 따른 추천이지 품질 보장이 아니다. 실제 계정/클라이언트에 표시되는 모델과 지원 설정을 확인한다.

현재 환경에서 설명을 확인한 추천 후보:
- `superpowers:systematic-debugging`: 녹화·현재 렌더·카메라 코드의 차이와 원인을 먼저 분리.
- `superpowers:executing-plans`: T1~T5의 순차 실행과 중단 조건 관리.
- `superpowers:test-driven-development`: 카메라 소스/보정·회귀 검사 변경. 미적 유사성은 화면 검토로 별도 판단.
- `superpowers:verification-before-completion`: 재개방·새 렌더·회귀 검사·AC 증거 확인 후 보고.

Codex 환경에서 각 스킬의 가용성과 지침을 다시 확인한다. 스킬이 요구하는 자동 커밋·설치 등이 있더라도 이 작업의 승인 경계를 우선한다. 하나의 Master .blend를 여러 에이전트가 동시에 수정하지 않는다. Blender 전용 스킬이나 MCP 연결은 실제 설치·권한 확인 전에는 전제하지 않는다. Three.js·Higgsfield·이미지 생성·UI 스타일 스킬은 이번 범위에 필요하지 않다.
