## 6. 차량·문·도크의 동작 계약

A: 같은 차량이 입고 마당에 접근한다. 문은 닫혀 있다.
B: 전진 선회 중 실제 중간 자세다. 견인부와 트레일러의 방향 차이·이동 위치가 읽힌다.
C: 후면이 도크를 향하게 정렬하고 정지한다. 정지 상태에서 문을 열어 측면에 고정한다.
D: C의 차체 방향을 유지한 채 짧게 후진하여 도크에 도착·정지한다. 하역 전이다.

D의 접속 위치 → 같은 자세로 도크에서 떨어진 C → A에서 C로 이어지는 전진 경로 순으로 검토한다.
B는 경로에서 선택한다. 이미지상의 B 위치나 임의의 180도 회전을 먼저 강제하지 않는다.
C에 전진으로 도착하는 마지막 이동 방향은 C의 운전석 전방과 일치해야 한다.
C→D에서는 같은 전방을 유지하면서 이동 방향만 반대인 후진이 된다.

기존 구현이 이미 이 관계를 충족하면 복제된 테스트 개체에서 우선 재생하고 검사한다.
실패한 조건에 한정해 최소 수정한다. 검증된 기능을 새 엔진으로 교체하지 않는다.
차량의 위치와 회전각을 독립 보간하거나 같은 경로를 시간차로 따라가게 하는 것만으로
연결점·차륜 이동·선회를 검증했다고 주장하지 않는다.

평면 저속 기구학 프록시로 충분하다. 정밀 차량 동역학이나 타이어 모델은 요구하지 않는다.
다만 실제 리그의 대표 차축·연결점·차체 전방을 정하고,
접지·연결점 보존·이동 접선·조향·후진 부호가 일관되는지 확인한다.
컨테이너와 트레일러의 상대 변환 및 전체 비례는 유지한다.

문은 후면의 2개 문짝만 움직이며 측면에 고정된다.
C의 정지 및 문 고정 완료 이전에 후진을 시작하지 않는다.
문짝이 옆벽·차체·도크를 관통하지 않게 하고, 내부를 보여 주기 위한 새 측면 문은 만들지 않는다.
D에서는 후면 바닥과 입고 바닥의 접속·높이 관계를 확인한다.
차량 바퀴는 마당에 남으며 도크에 운전석부터 들어가는 형태는 금지한다.

실제 마스터의 스케일과 기존 시험 수치를 우선 확인한다.
새 거리·허용 오차·충돌 여유·각도 기준은 출처 또는 시험 가정으로 config에 기록한다.
산업 표준·실제 시설 수치로 표시하지 않는다. 실패 후 통과시키려고 기준을 느슨하게 바꾸지 않는다.
기존 환경에서 성립하지 않으면 B/C 위치 조정을 검토하고, 큰 환경 변경은 승인 전 보류한다.

## 7. 카메라·시간·마스터 연결 계약

차량 경로 후보를 먼저 확인하되, 처음부터 카메라가 지나갈 바깥 공간을 예약한다.
그다음 테스트 사선 카메라가 차량 → 후면/도크 → 입고 바닥으로 시선을 넘기게 한다.
차량을 따라 한 바퀴 돌거나 후진에 맞춰 왕복·순간이동하지 않는다.
벽·차량을 통과하거나 내부를 보이게 하려고 도크 위치를 바꾸지 않는다.

사선 프리뷰에는 연속 카메라 하나만 사용한다.
진단용 탑뷰 카메라는 별도 출력용이며 본편의 숨긴 컷으로 사용하지 않는다.
후면 내부가 모두 보일 필요는 없지만, 실제 가시 범위에서 차량—도크—입고 바닥의 연결은 남긴다.

기존 자료상 S5는 B45=648부터 B56=900으로 이어지고,
정렬 f810, 문 개방 f811–842, 후진 f849–890이 기록되어 있다.
이 값은 기존 후보의 기록이다. 실제 입력 파일에서 먼저 검증한다.
초기 비교는 기존 fps와 프레임 범위를 유지한다.
테스트 시간 조정이 필요하면 master_frame/test_frame 대응을 기록하며 원본 키는 변경하지 않는다.

S5 진입과 S6 연결부에서 차량·컨테이너·문·카메라의 위치·회전·속도·렌즈·주시점을 기록한다.
단독 테스트 성공과 마스터 연결 가능 판정은 분리한다.
기존 S6 시작 상태에 맞추려면 다른 구간 변경이 필요한 경우 차이와 통합안을 보고하고 멈춘다.
최종 마스터 통합은 수행하지 않는다.

## 8. 실행 순서와 검증

단계 0 — 입력/기존 동작 조사
- 파일·환경·지침·선택된 기준을 확인하고 입력 해시와 원본 Scene 서명을 보존한다.
- 기존 S5를 탑뷰와 사선에서 확인하고 이미지 요구와의 차이를 기록한다.
- 기존 회귀 테스트를 원본 Scene 대상으로 안전한 출력 위치에서 재실행한다.
- 기존 실패와 신규 목표 미충족을 구분한다. 실패를 이번 변경의 성공으로 둔갑시키지 않는다.

단계 1 — 격리 테스트부터
- 테스트 전용 Object/Action/Camera/경로가 마스터와 분리되는 테스트를 먼저 작성한다.
- 임시 실행에서 테스트 차량 위치·문·Action·카메라 렌즈를 바꾸고
  같은 프레임의 원본 Scene이 변하지 않는지 검사한다. 이 변이는 제출 파일에 남기지 않는다.
- 외부 참조가 마스터의 가변 데이터로 새는지 검사한다.
- 저장·재개방·재실행 시 Scene/Collection/차량이 중복되지 않는지 검사한다.
- 새 계약은 통제된 작은 실패 입력으로 RED를 확인한다. 완성 마스터를 훼손해 RED를 만들지 않는다.

단계 2 — 기존 동작 재사용 및 최소 수정
- D/C 상태와 전진 선회·문·후진 계약을 검사한다.
- 연결점·대표 차축 이동·차체 방향·접지·컨테이너 고정 상태를 측정한다.
- 실패 원인을 확인한 기능만 수정하고 B를 실제 선회 중 의미 있는 프레임에서 선택한다.

단계 3 — 카메라 및 공간 검사
- 테스트 카메라의 연속 이동과 도크 접속부 가시성을 확인한다.
- 차량 전체·문짝·환경의 공간 겹침을 검사한다.
- 지지면 접촉, 도크 접촉, 내부 연결부 등 허용된 접촉과 관통을 구분한다.
- 차체 박스·카메라 점 검사만으로 정밀 충돌 검증을 주장하지 않는다.
  사용한 OBB/AABB/메시 근사, 샘플 간격, 제외 쌍과 남는 한계를 기록한다.
- 모든 테스트 정수 프레임과 선회·문 개방·접안 근처의 서브프레임을 검사한다.
  초기 서브프레임 간격은 기존 검토의 0.25프레임을 참고하되 실제 적용 범위를 보고한다.

단계 4 — 저장본 검증과 시각 검토
- 별도 새 Blender 프로세스에서 저장본을 다시 열어 테스트를 재실행한다.
- 핸들러·외부 런타임 없이도 저장된 동작이 재생되도록 결과를 키/필요 데이터로 보존한다.
- 탑뷰·사선의 같은 시간대 프리뷰를 출력하고 1배속 실제 재생을 확인한다.
- A/B/C/D 캡처와 문 개방 전후·접속부 캡처를 직접 본다.
- 원본 Scene에서 S1 프레이밍·전체 동작의 회귀 테스트를 다시 실행한다.
- 파일 해시, 코드/config 해시, 결과 파일과 AC 대응을 묶어서 보고한다.

기존 assertion을 새 테스트 Scene에 무조건 실행하지 않는다.
원본 회귀는 원본 Scene을 명시적으로 선택하고,
새 S5 검증은 source-map을 이용해 테스트 Scene의 개체에 수행한다.
기존 테스트가 Scene 이름이나 로그 경로에 의존하면 실행 어댑터로 대응하되 조건은 보존한다.

## 9. 수용 기준

AC-1 입력 추적:
실제 HEAD·입력 .blend SHA-256·참조 이미지·모델·도구 버전·가정을 manifest로 확인할 수 있다.

AC-2 마스터 비파괴:
원본 파일 해시가 불변이고, 새 검토본의 원본 Scene 의미 서명 및 기존 회귀 결과가 보존된다.
S1 프레이밍과 S1–S7의 기존 애니메이션을 포함한다.

AC-3 변경 격리:
테스트의 변환·문·Action·Camera 변경이 원본에 영향을 주지 않는다.
임시 변이 검사·참조 조사·재개방 결과를 제출한다.

AC-4 차량 동일성과 전진 선회:
같은 차량이 연결점과 컨테이너 고정을 유지하며 전진한다.
옆 미끄러짐·제자리 회전·갑작스러운 yaw 변경 없이 B를 지나 C에 도달한다.
측정값과 탑뷰/사선 프리뷰로 확인한다. 같은 자리에 각도만 다른 스틸은 증거가 아니다.

AC-5 정렬·문 개방:
C에서 후면이 목표 도크, 운전석이 마당을 향한다.
차체가 정지한 동안 문이 열려 측면에 고정되고 후진 경로는 비어 있다.
도크 축·후면 축·측방 오차·속도·문 상태를 수치와 캡처로 대응한다.

AC-6 후진·접속:
C→D는 동일 자세·접근축에서의 짧은 직선 후진이다.
도크까지 간격이 줄고 이동 부호가 차체 전방과 반대이며,
D에서 후면/입고 바닥 접속과 정지를 확인한다. 화물은 아직 내부에 남는다.

AC-7 공간·카메라:
검사한 범위에서 허용되지 않은 관통이 없고,
사선 연속 카메라가 바깥 경로에서 개방면으로 연결된다.
후면—도크—입고 바닥이 실제 보이는 범위에서 함께 읽힌다.
측정 검증과 시각 검토를 구분하고 정밀 물리·실차 안전 검증으로 확대하지 않는다.

AC-8 재현·재개방:
같은 기준 입력/config에서 재생성 가능하고 중복 데이터가 늘어나지 않는다.
새 프로세스로 연 파일의 상태·애니메이션·프레임 캡처를 대조한다.

AC-9 증거:
탑뷰·사선 영상, A/B/C/D 캡처, 상태/검증 JSON, 실행 로그,
원본 보존 비교와 최종 hashes가 같은 결과 파일 버전에 대응한다.

AC-10 경계와 승인:
S5 진입/S6 연결 상태의 차이를 integration-proposal.md에 기록한다.
기존 마스터에 후보 동작을 적용하지 않고, 승인 필요 항목과 통합 가능/불가 사유를 분리한다.
필수 AC 실패·미실행이 있으면 ‘완료’로 보고하지 않는다.

## 10. 명령·출력·보고

실제 실행 파일과 스크립트 인자를 먼저 확인한다. 아래는 새 스크립트용 명령 계약 예시다.
<...>는 실제 경로로 바꿀 값이며, 현재 존재하는 명령이라고 보고하지 않는다.

<blender> --background --factory-startup <기준-master.blend> --python-exit-code 1 --python <새-build_s5_test.py> -- --config <config.json> --output <새-검토본.blend>
<blender> --background --factory-startup <새-검토본.blend> --python-exit-code 1 --python <새-validate_s5_test.py> -- --scene S5_DOCK_TEST_v01 --output-dir <새-review>
<blender> --background --factory-startup <새-검토본.blend> --python-exit-code 1 --python <새-render_s5_review.py> -- --scene S5_DOCK_TEST_v01 --output-dir <새-preview>

새 스크립트는 절대 사용자 경로를 하드코딩하지 않고 입력·출력·Scene을 명시적으로 받게 한다.
입력과 출력이 같은 파일인 경우 기본 거부한다. 실행 실패는 nonzero 종료 코드로 전달한다.
순수 계산/설정 검사는 기존 unittest를 우선 활용하며 Blender 내 검사와 구분한다.
웹사이트 코드를 바꾸지 않으므로 무관한 npm 빌드로 이 작업 검증을 대신하지 않는다.

제출 파일:
- 기존 Scene + 격리된 S5 Scene이 함께 있는 편집 가능한 .blend.
- build/validate/render 스크립트, config, source-map 및 필요한 테스트.
- baseline/after 보존 서명, 격리 검사, 프레임/서브프레임 상태와 검증 JSON.
- 탑뷰/사선 MP4 또는 인코더가 없을 때 동일 프레임 PNG 시퀀스.
- A/B/C/D 스틸, 문·도크 접속부 확대 증거.
- README, report, integration-proposal, hashes.

README에는 실제로 실행된 환경과 재현 명령을 남긴다.
보고서에는 변경 파일 목록·diff, 실제 입력과 결과 해시,
AC별 상태/증거, 실행 명령/종료 코드, 기존/신규 실패,
미실행 검사/이유, 공유/격리한 데이터, 설계 이탈과 남은 위험을 적는다.

## 11. 중단 조건·공통 경계

다음은 관련 작업을 중단하고 근거·대안을 보고한다.
- 마스터 입력을 확정할 수 없거나 파일/참조/실행 환경에 접근할 수 없음.
- 격리를 보장할 수 없거나 원본 .blend·기존 Scene이 변한 사실을 발견함.
- 이미지 요구를 맞추려면 창고/도크/전체 세계의 큰 재배치가 필요함.
- 기존 구간·공통 자산 인터페이스·카메라 경계의 변경이 필요함.
- 새 유료 서비스, 외부 자산 업로드, 권한/보안 설정 변경이 필요함.
- 실패한 검사를 우회하거나 거짓 성공 표시를 해야만 진행 가능한 상태.

중요 충돌이 없는 범위 내 작은 조정은 이유와 영향·재검증을 기록하고 진행한다.
코드만 작성했고 Blender 실행을 못 했다면 ‘구현안 작성 / 실행 검증 미완료’로 보고한다.
블록아웃은 상징적 동선 검토이며 실제 시설·운영 수치·안전 인증이 아니다.

테스트 삭제·비활성화·규칙 완화로 통과를 꾸미지 않는다.
비밀키·실제 개인정보를 코드·로그·샘플에 넣지 않는다.
기존 무관한 변경과 사용자의 미저장/저장 작업을 보존한다.
승인 없는 운영 데이터 변경·운영 배포·유료 호출·강제 push·무관한 변경 덮어쓰기를 금지한다.
라이브러리 추가는 이유·영향을 보고하고 설치/권한 승인 정책을 따른다.

최종 판정은 ‘수용 가능한 테스트 후보’, ‘재작업 필요’, ‘증거 부족’ 중 하나로 제시한다.
테스트 후보 수용과 마스터 통합·운영 공개 승인은 별개다.
